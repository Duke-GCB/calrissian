## Update: test 229 passes after fixing output collection

A focused rerun first reproduced the original failure:
before-fix log (transient log not retained).
The tool stages two input directories (`testdir` and `rec`) through
`InitialWorkDirRequirement` and returns the files matched by `testdir/a` and
`rec/B`.

Calrissian mounted those directories into the task pod, but collected outputs
from the runner's filesystem. It omitted cwltool's `relink_initialworkdir()`
step, leaving those paths absent from the runner's output directory and
producing an empty output array.

`CalrissianCommandLineJob.finish()` now calls that helper before output
collection. A filesystem regression test checks that both staged directories
are traversable when collection starts. The full unit suite passed with
364 passed and 1 skipped.

After rebuilding the production-derived conformance image, this command passed
with test-container exit code 0:

```sh

```

Evidence: after-fix log (transient log not retained).

## Update: tests 258 and 376 pass after correcting runtime resources

Calrissian's custom `select_resources()` hook replaced cwltool's resource
selection but omitted `tmpdirSize` and `outdirSize` and did not round RAM to
integer MiB. The hook now provides both storage fields and rounds RAM and
storage minima up, matching cwltool's default selection. Rounded RAM requests
are checked against the executor's resource envelope.

Test 258 requests RAM `254.1–254.9`, temporary storage `255.1–255.9`, and output
storage `256.1–256.9` MiB. Its selected runtime values are now `255`, `256`, and
`257`, respectively.

Once the missing fields were restored, test 376 exposed a second issue:
Calrissian's internal `coresMax`, `ramMax`, `gpus`, and `cudaDeviceCountMax`
fields leaked into the CWL runtime object. `SelectedResources` now carries
pod limits as metadata outside its runtime dictionary. Pod construction still
uses the limits, and GPU accounting uses the selected `cudaDeviceCount` when
present. CPU-only tools expose the standard runtime fields without those
internal extras.

Both focused tests passed with container exit code 0 after rebuilding the
production-derived conformance image:

- Test 258 passing log (transient log not retained).
- Test 376 passing log (transient log not retained).

Regression coverage checks storage fields, rounding, capacity checks, runtime
keys, pod limits, and GPU accounting. The full unit suite reported **376 passed,
1 skipped**. Storage values are reported to CWL expressions; this change does
not reserve PVC space or enforce storage quotas. The subsequent full-suite rerun also passed both cases.

## Update: tests 333, 334, and 340 pass

Tests **333** (`iwd-fileobjs1`) and **334** (`iwd-fileobjs2`) declare a File and
Directory directly in `InitialWorkDirRequirement.listing`; test 334 nests the
objects in an array. Their command is `true`, so the outputs must preserve the
staged input file's contents and the directory's recursive listing. Both passed
with the relinking fix introduced for test 229.

Test **340** (`iwd-subdir`) emits `testdir/c` from the first workflow step and
passes that Directory into a second step. Relinking fixed the original missing
output, but exposed a downstream Kubernetes mount failure:
`failed to create subPath directory for volumeMount`.
The generated mount selected the output PVC and a subPath traversing the
runner's symlink back to the input PVC. Kubernetes could not use that path.

`KubernetesVolumeBuilder.add_volume_binding()` now resolves the source with
`os.path.realpath()` before selecting the PVC and calculating its subPath.
The second step therefore mounts the actual directory from the input PVC,
while preserving the requested container path. Regression tests cover a
symlink across two mounted PVC paths, including a parent subPath, and rejection
of links to unmounted paths.

After rebuilding, all three focused tests passed with exit code 0:

- Test 333 passing log (transient log not retained).
- Test 334 passing log (transient log not retained).
- Test 340 passing log (transient log not retained).

The full unit suite reported **378 passed, 1 skipped**. Test 340 still emits
upstream duplicate-object-ID warnings, which do not prevent it from passing.
The subsequent full-suite rerun also passed all three cases.

## Update: test 368 passes after filename and redirection fixes

Test **368** (`filename_with_hash_mark`) reads a File whose URL-quoted location
refers to `item #1.txt`, using the tool's `stdin` binding. A focused rerun
reproduced the original validation failure (transient log not retained).

Two issues prevented it from passing:

1. Calrissian supplied its own LoadingContext without passing through the
   path-check setting, leaving cwltool's strict filename checking enabled.
   Calrissian now defaults to the supported relaxed mode and explicitly passes
   the setting into its loading context. This replaces obsolete global-regex
   overrides in the Dask schema setup. To request strict checks, use
   `"relax_path_checks": false` in a Calrissian JSON configuration file supplied
   through `--conf` or `$HOME/.calrissian/default.json`.
2. After validation succeeded, the shell command still included an unquoted
   stdin filename. The space split the path and `#` began a shell comment.
   `container_args()` now shell-quotes stdin, stdout, and stderr paths while
   preserving the redirection operators.

Regression tests exercise cwltool's actual filename checker in relaxed and
explicit strict modes, propagation of the setting, and a real shell command
with spaces, hashes, and single quotes in all three redirection paths.
The full unit suite reported **381 passed, 1 skipped**.

After rebuilding the production-derived conformance image, the focused test
passed with container exit code 0:
passing log (transient log not retained).
The retained Job is `conformance-1-2-1-368-e21bf8cb`. The subsequent full-suite rerun also passed this case.

## Update: ToolTimeLimit is explicitly unsupported

Calrissian does not enforce execution time limits. A required `ToolTimeLimit`
now raises `UnsupportedRequirement` before the task pod is submitted, including
zero limits and expression-valued limits. Optional `ToolTimeLimit` hints are
ignored with a warning; they do not provide timeout enforcement.

This avoids silently accepting a required execution constraint that the
Kubernetes backend cannot currently enforce. No execution timer or pod deadline
has been introduced. Tests 217, 220, 222, and 225 remain recorded above as
historical failures. After rebuilding the image, a focused rerun of test 217
reported **0 passed, 1 unsupported feature**, confirming the classification:
rerun log (transient log not retained).
The cwltest process exited 0 for this unsupported-only result; this is not a
passed test. The full unit suite reported **384 passed, 1 skipped**. The subsequent full suite reported seven ToolTimeLimit cases as unsupported,
alongside two unsupported dockerOutputDirectory cases.

See the [full run log](../../conformance/results-v1.2.1.txt) and the
[explanation of v1.0 test 173](v1.0-test-173.md) for the corresponding
Docker entrypoint failure.
