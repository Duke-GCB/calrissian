# Calrissian - CWL Conformance Tests

Run [CWL conformance tests](https://github.com/common-workflow-language/cwltest)
on a local Minikube cluster using Task, Skaffold, and the Helm chart. The
supported suites are CWL v1.0.2, v1.1.0, v1.2.0, and v1.2.1.

See the [latest complete results](../docs/comformance/latest-results.md) for
verified totals and remaining failures.

## Local development with Task and Skaffold

This setup follows the image-build and Helm session approach in
[dev-platform-calrissian](https://github.com/fabricebrito/dev-platform-calrissian).
Install Docker, Minikube, Task, Skaffold v2, Helm v3, and kubectl first.
Run from the repository root:

```sh
task conformance:cluster
skaffold dev
```

The task starts the `calrissian-conformance` Minikube profile with 6 CPUs and
12 GiB RAM, allowing headroom above the tests' 4 CPU / 8 GB envelope. Override
settings with, for example, `task conformance:cluster CPUS=8 MEMORY=16384 DRIVER=docker`.
The profile uses the Docker container runtime and the standard Minikube storage
provisioner on a single node. Skaffold builds directly in that Docker daemon;
a containerd-based profile is not supported by this setup.

Skaffold first builds the production image from `./Dockerfile`, then extends it
with `conformance/Dockerfile.conformance` to install `cwltest`. Existing Python
packages are constrained to their production versions during this installation.
It installs the Helm chart in the `calrissian-conformance` namespace. It creates
the shared data/output PVCs, RBAC, a persistent `calrissian-session` deployment,
the data staging Job, and the `inspect-volumes` pod used for copying badges.
The default service account also receives runner permissions for the existing
version-specific test Jobs. The session image uses Skaffold's resolved image;
the local `conformance:latest` tag is retained for those test Jobs.

The 1.2.1 suite uses the released `v1.2.1` tag and writes results to
`badges/1.2.1`, which the badges above reference.
Archive URLs and filenames are configured under `staging.archives` in
`chart/values.yaml`. Override them with a Helm values file or, for example,
`--set staging.archives.v1_2_1.file=v1.2.1.zip`. If an archive extracts to a new
directory, update the corresponding test Job's suite path as well.

Staging runs as a Helm post-install/post-upgrade hook. Helm replaces the previous
`stage-conformance-test-data` Job before each deployment and waits for completion,
so changes to archive values or the staging command do not attempt to patch an
immutable Job template. Extraction overwrites existing files so staging can run
again. The completed hook Job remains available for logs until the next upgrade.
Helm does not remove hook Jobs on uninstall; delete it explicitly when needed:
`kubectl --context calrissian-conformance -n calrissian-conformance delete job stage-conformance-test-data --ignore-not-found`.


In another terminal, wait for data staging before running a suite:

```sh
kubectl --context calrissian-conformance -n calrissian-conformance wait \
  --for=condition=complete job/stage-conformance-test-data --timeout=300s
kubectl --context calrissian-conformance -n calrissian-conformance wait \
  --for=condition=Ready pod/inspect-volumes --timeout=120s
cd conformance
./run-job-1-2.sh
```

The existing scripts use the current kubectl context, which the cluster task sets
to `calrissian-conformance`. Other suites use `run-job-1-0.sh`, `run-job-1-1.sh`,
and `run-job-1-2-1.sh`. Delete a previous suite Job before rerunning it. The
scripts save logs and copy badges; inspect the Job's completion status to confirm
the result. Skaffold manages the development environment, not these test Jobs.

To run a single numbered test after staging completes, run from the repository
root:

```sh
task conformance:test VERSION=1.0 ID=173
```

Supported suite versions are `1.0`, `1.1`, `1.2`, and `1.2.1`. `ID` is the
suite's numeric test selector (`cwltest -n`). Each invocation creates a unique
Job, streams and saves logs to `conformance/conformance-<version>-<id>-<suffix>.txt`,
and copies badges into a separate directory under `conformance/badges/` using
the inspection pod. Task fails if the test container fails or badge collection
fails. Jobs are retained for inspection; Ctrl+C stops the run and deletes its
Job. To preview the generated Job, use
`python3 conformance/run-test.py --version 1.0 --id 173 --dry-run`.

### Network access policies

See the [published cluster guide](../docs/cluster-configuration.md#enforcing-cwl-network-access)
for matching policy/label examples, deployment configuration, and an
allowed/denied/allowed HTTP validation procedure.

The chart's `networkAccess` values configure `allowedLabels` and `deniedLabels`
for CWL task pods. Both maps must contain a shared key with different values,
so the selectors cannot overlap. The chart generates label files and
Calrissian's `default.json` in the `conformance-network-config` ConfigMap.
The session and suite Jobs mount it at `/home/calrissian/.calrissian`; single-test
Jobs inherit the same mount. The chart supplies this ConfigMap for all supported runs.

With `networkAccess.enabled: true`, network-disabled task pods have all egress
blocked, including DNS; network-enabled task pods have unrestricted egress.
Runner, staging, and inspection pods do not receive these task labels. Other
NetworkPolicies can add permissions, since Kubernetes policy rules are additive.
Set `networkAccess.enabled: false` to disable the chart's labeling and policies.

The cluster creation task now selects Calico with `--cni calico`. Existing
clusters must already have a policy-enforcing CNI or be recreated with the task
before relying on these policies. Applying the chart does not change a cluster's
CNI. See [Minikube network policy support](https://minikube.sigs.k8s.io/docs/handbook/network_policy/).

Calrissian uses the boolean `NetworkAccess.networkAccess` value to select the
allowed or denied labels. Without an explicit requirement, CWL v1.0 defaults
to network access enabled, while CWL v1.1 and v1.2 default to disabled.

For an interactive session:

```sh
kubectl --context calrissian-conformance -n calrissian-conformance exec \
  -it deployment/calrissian-session -- bash
```

Stopping `skaffold dev` removes its Helm release, including PVCs and their test
outputs. Copy any results first. The Minikube cluster remains available; remove
it explicitly with `task conformance:cluster:delete` when done. To stop the
cluster while preserving its data, use `task conformance:cluster:stop`. Restart
it with `task conformance:cluster`.

## Inspect storage and collect badges

Skaffold and Helm are the supported environment setup. The chart creates the
`inspect-volumes` pod; no separate inspection manifest needs applying.

```sh
kubectl --context calrissian-conformance -n calrissian-conformance exec \
  -it inspect-volumes -- /bin/bash
```

The pod mounts staged input data at `/conformance` and results at `/output`.
The run scripts copy badges automatically. To copy them manually from the
repository root, for example:

```sh
kubectl --context calrissian-conformance -n calrissian-conformance cp \
  inspect-volumes:/output/badges-1.2.1/ conformance/badges/1.2.1
```

The version-specific `ConformanceTestsJob-*.yaml` files remain inputs to the
full-suite and single-test runners. They require the chart-managed storage,
staged data, permissions, and conformance image.

### Tool execution time limits

`ToolTimeLimit` is not supported. Required declarations are rejected before
Calrissian submits a task pod; optional hints are ignored with a warning.
Calrissian does not impose a Kubernetes pod deadline as a substitute, since
pod startup and image-pull time are outside CWL command execution time.

### Runner and task ServiceAccounts

The chart binds management permissions only to `calrissian-sa`, used by the
interactive session and conformance/Dask runner Jobs. Task pods use
`calrissian-workflow`, which has token automount disabled and no chart-created
RoleBindings. `default` is not included in the runner RoleBinding. The chart's
runner configuration selects the workflow account even when network policies
are disabled. Use the updated Job manifests when upgrading an existing setup.

After deployment, verify effective namespace and cluster-wide RBAC:

```sh
python3 examples/service-account-separation/check-permissions.py
```

See [cluster configuration](../docs/cluster-configuration.md) for a production
example, account selection, and migration from the old default-account grants.
